# JJC 对局详情玩家跳转对局查询计划

状态：已完成，已归档
更新时间：2026-06-17

## 需求澄清

用户目标：

- 在竞技场排名页 `public/jjc-ranking-stats.html` 中，点开某场对局详情后，点击任意玩家信息，跳转到 JJC 对局查询页并查看该玩家的战绩列表。
- 在 JJC 对局查询页 `public/jjc-synced-matches.html` 中，点开某场对局详情后，点击任意玩家信息，切换到该玩家的战绩列表。

当前结论：

- 两个页面都已经具备“打开对局详情”的能力。
- JJC 对局查询页已经支持基于 `server` 与 `name` 的页面初始化和查询。
- 当前缺口仅在前端详情弹窗内，玩家卡片没有“可导航到该玩家战绩”的行为。

本次改动默认假设：

- “某个人的信息”指详情弹窗中的参赛玩家卡片，而不是装备图标、奇穴标签或队伍标题。
- 目标页面是现有 JJC 对局查询页，生产路径为 `/jx3/jjc-synced-matches.html`，本地直出时可能是 `/public/jjc-synced-matches.html`。
- 只要玩家具备 `server` 和 `role_name`，就允许跳转；不额外依赖 `global_id`、`role_id` 或后端新增解析。

## 目标

- 让两处对局详情弹窗中的玩家卡片具备明确、稳定的点击跳转行为。
- 复用现有 JJC 对局查询页的搜索与加载逻辑，不新增 API，不改变数据来源。
- 保持现有详情展示结构、焦点玩家高亮、装备与奇穴展示不变。

## 非目标

- 不修改 `src/api/routers/`、`src/services/jx3/`、`src/storage/` 的业务逻辑。
- 不新增数据库字段、索引、缓存或同步队列行为。
- 不改竞技场排名页中“角色近期战绩”弹窗的既有查询口径。
- 不把详情弹窗改造成 SPA 路由系统，也不抽离公共前端模块。

## 影响范围与分层边界

本次改动应限定在静态前端层：

- `public/jjc-ranking-stats.html`
  - 为对局详情中的玩家卡片增加可点击语义、数据属性和跳转函数。
  - 在 match 弹窗点击事件中优先识别玩家卡片点击，再执行页面跳转。

- `public/jjc-synced-matches.html`
  - 为对局详情中的玩家卡片增加可点击语义、数据属性和同页切换函数。
  - 在 match 弹窗点击事件中识别玩家卡片点击，复用现有查询流程重新加载角色信息和战绩列表。

明确不动：

- `src/api/routers/jjc_ranking_stats.py`
- `src/services/jx3/jjc_ranking_inspect.py`
- `src/storage/mongo_repos/*`
- `README.md`、`docs/references/runbook.md`

理由：

- 这是前端交互补齐，不涉及 API 合约变化、数据结构变化或运行方式变化。
- 按仓库当前分层规则，交互逻辑应收敛在静态页面，而不是把纯导航需求下沉到 service/router。

## 现状分析

已确认的现状：

1. `public/jjc-ranking-stats.html`
   - 通过 `renderTeam(team, focusPlayer)` 渲染详情弹窗中的参赛玩家卡片。
   - `matchModal` 目前只处理关闭弹窗，不处理点击玩家后的导航。
   - 页面已有 `loadRoleRecent(server, name, identityHints)`，但这是排名页内部的“近期战绩”弹窗，不是目标页面。

2. `public/jjc-synced-matches.html`
   - 同样通过 `renderTeam(team, focusPlayer)` 渲染详情弹窗中的参赛玩家卡片。
   - 页面已具备 `searchRole()`、`setServerInputValue()`、`nameInput.value = ...`、URL 参数初始化等完整查询链路。
   - `contentPanel` 负责列表行为，`matchModal` 目前只负责关闭详情，不负责玩家切换。

3. 页面路径口径
   - 生产静态页使用 `/jx3/<page>.html`。
   - 本地 bot 直接暴露静态目录时使用 `/public/<page>.html`。
   - 因此跳转目标不能写死完整绝对路径，需要根据当前页面路径推导。

## 业务规则

1. 点击有效性
   - 只有当玩家卡片同时具备非空 `server` 和 `role_name` 时，点击才生效。
   - 若缺任一字段，则保持纯展示，不触发空查询。

2. 排名页跳转规则
   - 在 `public/jjc-ranking-stats.html` 的对局详情中点击玩家卡片后，跳转到 JJC 对局查询页。
   - 跳转地址需带上 `server` 和 `name` 查询参数。
   - 该跳转应以新页面方式打开，不覆盖当前排名页上下文。
   - 若能安全复用当前页面目录，则优先生成同源相对 URL，避免硬编码域名和 API 前缀。

3. 对局查询页切换规则
   - 在 `public/jjc-synced-matches.html` 的对局详情中点击玩家卡片后，不新开页面，直接在当前页面切换到该玩家。
   - 应关闭当前详情弹窗，更新搜索输入框与地址栏参数，并调用现有查询流程加载该玩家战绩。
   - 该切换需要写入浏览器历史栈，使浏览器后退可以回到切换前的角色。
   - 新查询应覆盖当前角色上下文，使后续“加载更多”“加入同步队列”“刷新战绩”等操作都绑定到新角色。

4. 交互兼容规则
   - 不能影响当前点击对局行打开详情的行为。
   - 不能影响当前焦点玩家高亮逻辑。
   - 不能影响装备图标、奇穴 tooltip、队伍标题等现有交互。

## 技术方案

### 方案选择

采用“纯前端增量导航”方案，不新增后端能力。

原因：

- 目标行为本质是页面导航与已有查询流程复用，不需要新数据。
- 后端已有 `server + name` 查询入口，前端参数已足够。
- 改动最小，风险集中在两个静态页，可快速验证和回滚。

### 具体设计

1. 玩家卡片数据透传
   - 在两个页面的 `renderTeam(team, focusPlayer)` 中，为玩家卡片根节点增加：
     - `data-player-server`
     - `data-player-name`
     - 可选 `data-role-nav="1"` 标记
   - 同时补充交互样式：
     - 鼠标态可点击
     - 焦点态不破坏现有 `.focus` 样式

2. 排名页跳转函数
   - 在 `public/jjc-ranking-stats.html` 内新增小型工具函数：
     - 根据 `window.location.pathname` 推导目标页基础路径。
     - 使用 `URL` 或 `URLSearchParams` 拼接 `server` 与 `name`。
     - 调用 `window.open(..., "_blank")` 或等效方式执行新开页跳转。
   - 不依赖后端配置或新的全局常量。

3. 对局查询页同页切换函数
   - 在 `public/jjc-synced-matches.html` 内新增小型工具函数：
     - 写入 `serverInput` 和 `nameInput`
     - 使用 `history.pushState` 写入新的 `server` / `name` URL 参数
     - 关闭当前 `matchModal`
     - 调用现有 `searchRole()` 触发整页角色上下文刷新
   - 同时补齐 `popstate` 响应，使浏览器后退时能按地址栏参数恢复上一角色查询。
   - 不直接手工改 `currentRole`，优先走现有查询入口，避免漏同步状态与分页状态。

4. 弹窗事件处理顺序
   - 在两个页面的 `matchModal.addEventListener("click", ...)` 中，优先识别玩家卡片点击。
   - 若命中玩家卡片，执行导航并 `return`。
   - 其余点击继续保留原关闭弹窗等行为。

## 风险与兼容性

主要风险：

1. 路径推导错误
   - 风险：生产环境 `/jx3/` 与本地 `/public/` 路径不同，若写死路径会导致跳错页面。
   - 处理：基于当前 `pathname` 推导同目录目标页文件名，只在必要时兜底默认文件名。

2. 事件冒泡冲突
   - 风险：玩家卡片点击可能与弹窗关闭逻辑、tooltip 点击或其他容器点击冲突。
   - 处理：在玩家导航分支命中后立即返回，必要时阻断默认行为。

3. 同页切换状态残留
   - 风险：`currentRole`、分页状态、候选角色状态、matchModal 状态可能部分沿用旧角色。
   - 处理：统一走现有 `searchRole()`，并在切换前关闭 `matchModal`，让已有逻辑重建页面状态。

4. 浏览器历史不一致
   - 风险：当前页切角色如果只改 DOM 不改历史栈，浏览器后退无法回到上一个角色；如果只写 URL 不监听 `popstate`，后退后页面数据会和地址栏不一致。
   - 处理：切角色时使用 `history.pushState`，并在 `popstate` 中按 URL 参数重新触发搜索或恢复空态。

5. 无效玩家数据
   - 风险：部分历史详情可能缺服名或角色名。
   - 处理：无效时不导航，不抛错误，不污染地址栏。

6. 详情角色名带服务器后缀
   - 风险：部分详情玩家 `role_name` 可能已经是 `角色名·服务器` 或 `角色名@服务器`，如果直接作为 `name` 参数跳转，会与独立 `server` 参数重复，导致 JJC 对局查询页按错误角色名查询不到结果。
   - 处理：前端跳转数据只在角色名末尾精确匹配 `·<server>` 或 `@<server>` 时剥离后缀；普通包含分隔符的角色名不做额外处理。

## 验证计划

自动化验证：

- 本次主要是静态 HTML 内联 JS 改动，仓库内没有现成前端自动化测试基座。
- 不新增伪自动化脚本，避免为一次小交互扩散工具链。

最小离线检查：

- 检查修改后两个 HTML 中新增 JS 是否存在明显语法问题和未定义引用。
- 逐处确认新函数只依赖当前页面已有变量和 DOM 节点。

手工回归：

1. 排名页跳转
   - 打开竞技场排名页。
   - 进入角色近期战绩。
   - 打开任意单场对局详情。
   - 点击任意具备服务器和角色名的玩家卡片。
   - 预期：新开一个 JJC 对局查询页页签，地址栏带 `server`、`name` 参数，并自动开始该玩家查询；原排名页保持不变。

2. 对局查询页同页切换
   - 打开 JJC 对局查询页并查询一个已有角色。
   - 打开任意单场对局详情。
   - 点击另一个玩家卡片。
   - 预期：关闭详情弹窗，搜索框切换为新角色，地址栏参数同步变化，页面展示新角色战绩列表。

3. 浏览器后退恢复
   - 在对局查询页连续切换至少两个角色。
   - 使用浏览器后退。
   - 预期：地址栏回到上一个角色参数，页面数据也恢复到上一个角色，而不是只变化 URL。

4. 异常数据保护
   - 构造或选择缺少 `server` 或 `role_name` 的玩家信息。
   - 预期：不跳转、不报错、不触发空查询。

5. 现有行为不回归
   - 点击对局行仍能正常打开详情。
   - 焦点玩家高亮、装备、奇穴 tooltip 仍正常显示。

## 回滚方案

回滚粒度仅限两个静态页面：

- 删除玩家卡片上的新增 `data-*` 属性和交互样式。
- 删除新增导航函数或同页切换函数。
- 恢复 `matchModal` 点击事件为原始仅关闭弹窗逻辑。

不需要数据库回滚、接口回滚或缓存清理。
