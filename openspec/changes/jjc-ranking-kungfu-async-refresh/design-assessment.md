## 必须修正的设计问题

### 1. 数据归属改变后，原子提交要求不再成立

依据：`specs/jjc-kungfu-refresh/spec.md:31`、`design.md:130` 的同文档发布前提，与最新候选拆集合冲突。

建议：采用“先有条件写角色结果，再确认队列”的至少一次处理。结果写成功但确认前退出，允许恢复后重复执行；不得先确认再写结果。无需为维持旧承诺直接引入多文档事务。

建议验证，未执行：分别在角色写入前、写入后确认前、确认后模拟退出；成功值不丢失，任务可恢复。

### 2. 发布版本必须跨当前角色的重试及作用域切换可比较

依据：旧 `design.md:71` 按赛季/算法分任务，`design.md:93` 依赖旧任务只能写旧结果文档。新候选所有任务写同一个角色心法槽位，这项隔离不再自然成立。

场景：旧赛季任务 generation=30 迟到，新赛季任务 generation=1 已成功。简单比较各自 generation 会覆盖新值。只在队列表检查 token，也不能原子保护另一集合。

建议：首版固定当前 3v3，一角色长期保留一条任务；领取时角色级 generation 递增，切赛季/算法不归零，角色结果只接受更大的 publish_version，并匹配必要定位字段。队列不得在活动执行期间删除重建。赛季/算法仍须校验，版本大小不替代作用域合法性。

该简版保证“旧任务不覆盖更新的成功结果”，不保证“租约到期后旧任务绝对不能发布尚无更新成功值的结果”。若要求后者，需角色侧执行令牌/租约或事务，是额外复杂度。多个旧新配置同时运行也不能仅靠版本大小解决，须另有明确部署与作用域切换协议。

建议验证，未执行：同作用域旧结果迟到、跨赛季/算法迟到、结果写成功但队列确认失败、旧任务失败/释放不影响新任务。

### 3. 心法时间不能混入身份更新时间

依据：`src/storage/mongo_repos/role_identity_repo.py:27` 的身份 CAS 包含顶层 updated_at；同文件 `:239` 的同名候选排序使用 last_seen_at/updated_at。普通画像与升级更新采用字段级 `$set`，新增子对象具备保留基础。

建议：心法发布仅更新独立子对象，以 verified_at 表示成功时间；不推进身份顶层 updated_at、last_seen_at 或画像对局水位，不把心法字段加入身份全画像 CAS。修改仓储与数据库文档中“不存心法”的职责描述。

建议验证，未执行：心法并发刷新不造成未变化身份资料的恢复操作失配；身份升级/查询 ID 回滚保留心法；同名候选不会仅因刷新心法改变排序。

### 4. 批量解析身份必须验证榜单 ID，不能直接接受名称 fallback

依据：`role_identity_repo.py:455` 的最佳身份解析有名称回退；现有角色更新的强冲突保护不等于所有榜单 ID 都已精确匹配。

建议：新增批量解析复用现有能力时，对榜单携带的区服、角色 ID 与候选精确核对；明确冲突记 unknown，不能借同名把另一角色心法复用过来。缺心法者也必须登记刷新，不复用 `jjc_ranking.py:835` 的“已有心法才入部分历史队列”条件。

建议验证，未执行：同服同名不同角色 ID、弱身份升级、榜单无法定位、缺心法仍入队、心法刷新不改完整历史同步水位。

### 5. 严格赛季证据规则可能改变原算法可用性

依据：现有 `kungfu.py:405`、`:483` 及 `indicator_utils.py:29` 不足以证明旧判定具备计划中全部赛季/比赛类型证据校验；`design.md:93` 却要求不足十胜且 indicator 无赛季证据时一律未知。

建议：先检查真实脱敏响应契约，区分“结果缓存按当前赛季隔离”和“上游输入可被证明属于该赛季”。不能把请求时的配置赛季伪装成上游证据；若新增过滤会降低覆盖率，应显式说明行为变化，不能同时宣称算法与可用性完全不变。

建议验证，未执行：不足十胜、缺赛季/比赛类型字段、跨赛季历史、有效 indicator 回退。现有十胜多数和平票口径继续用特征测试固定。

## 建议的首版边界

结果：`role_identities.jjc_kungfu` 保存规范心法、赛季/类型/算法、来源、成功时间、必要输入时间、样本数和 publish_version。它是主打心法判定，不是即时装备心法。

任务：独立队列一角色一条当前3v3任务，保存目标 scope、status、next_run_at、generation、lease_token、lease_expires_at、最近上榜时间、失败次数与简短错误码。主键去重、到期领取索引、租约回收索引作为起点，按实际查询与 explain 决定扩展。

流程：批量解析/读角色 → 幂等登记全部可定位榜单角色 → 本地结果直接统计/缺失未知 → 后台领取 → 查询与既有规则判定 → 有条件写角色 → 条件确认任务。失败保留成功值，后台不改变已生成快照。

时效：统一刷新周期内为fresh；超过周期但未超最大年龄为stale，可使用并刷新；超最大年龄记unknown。具体初值需结合榜单03:00/21:00采集节奏、接口耗时、容忍度确定。输入观测时间不得等同于最近比赛时间。

历史：角色身份归档定义为身份画像审计，不因心法刷新持续归档。现有不同读取 projection 不保证档案含完整心法；统计快照承担本次采用值的历史记录。

## TDD 建议收敛为四个纵向闭环

1. 角色心法读写、时效、身份更新保留、旧判定特征测试。
2. 入队去重、领取、条件发布、确认、失败与崩溃恢复；真实隔离 Mongo 验证竞争窗口。
3. 单消费者运行、薄异步查询、超时、退避、启停、QQ离线。
4. 排名批量读取、未知名次与人数守恒、快照冻结、冷热均零前台心法外呼；之后预热轮转与性能实验。

任务和测试数量不是复杂度结论的依据；删除额外需求后重排测试矩阵，不为减少数量删除可靠性测试。
