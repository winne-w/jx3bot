## Purpose

为角色维护最近成功判定的3v3主打心法，独立队列负责定期刷新。以可恢复的至少一次执行替代结果/任务同文档提交，不引入分布式调度平台。

## ADDED Requirements

### Requirement: 成功心法属于角色画像

系统 MUST 将新模式唯一权威心法保存于 `role_identities.jjc_kungfu`，包含规范心法、赛季/类型/算法、来源、独立成功时间和发布版本。心法更新 MUST 不推进身份顶层更新时间、最近见到时间或画像/历史同步水位，身份资料更新 MUST 保留心法子对象。

#### Scenario: 身份升级与心法刷新并发
- **WHEN** 同角色升级身份键或恢复查询ID，同时后台刷新心法
- **THEN** 稳定角色_id不因心法改变，身份更新保留心法
- **AND** 心法写入不因修改顶层updated_at造成身份CAS额外冲突

#### Scenario: 查询失败但已有成功心法
- **WHEN** 网络失败、数据不可判定或身份定位冲突
- **THEN** 原心法及verified_at保持不变，仅记录任务失败并安排重试

### Requirement: 刷新队列按角色长期去重

系统 MUST 为每个可定位榜单角色维护一条当前3v3长期任务，角色_id为键；重复登记 MUST 不重置租约、代次、退避或成功时间。周期刷新与失败重试 MUST 通过next_run_at调度。代次 MUST 在重试、重启及赛季/算法切换时保持角色级单调，不允许活动期间删除重建或归零。

#### Scenario: 无心法角色重复上榜
- **WHEN** 同一角色无成功心法且被多个重叠统计重复登记
- **THEN** 仍只有一条任务，缺心法不影响入队，登记不绕过已有退避

#### Scenario: 作用域切换
- **WHEN** 已停止旧消费者并切换当前赛季或算法
- **THEN** 原任务条件切换目标、撤销旧token、递增代次，原角色结果保留但须通过读取scope校验
- **AND** 旧配置与新配置不得长期并存写入

### Requirement: 任务领取与恢复有条件执行

系统 MUST 原子领取到期且仍活跃的任务并生成唯一token及递增代次；确认成功/失败 MUST 同时匹配角色、scope、running状态、token、代次和未过期租约。进程中断后 MUST 回收过期任务，不能无条件释放后来任务。失去追踪活跃性 MUST 停止继续领取，不删除历史成功结果。

#### Scenario: 过期任务被新执行者接手
- **WHEN** A租约到期，B领取同角色的新代次
- **THEN** A的失败、确认或释放不能改变B任务，B能继续处理

#### Scenario: 离榜后重新上榜
- **WHEN** 追踪期限已过的角色重新上榜
- **THEN** 更新其追踪时间，已到期任务可恢复领取，已有退避和发布代次不被清空

### Requirement: 发布先于队列确认且版本单调

系统 MUST 先以角色_id、必要定位字段及发布版本条件更新角色，再确认任务完成。角色仅接受高于已有成功版本的新结果；失败或确认异常 MUST 不撤回成功结果。系统 MUST 允许中断后的重复执行，不能宣称跨集合exactly-once或同一提交边界。

#### Scenario: 结果保存后进程退出
- **WHEN** 角色心法已保存但队列确认前进程退出
- **THEN** 结果仍可用于统计，任务到期恢复后可重新查询并发布更大版本，不出现已确认成功但结果未保存

#### Scenario: 旧结果在新成功值之后返回
- **WHEN** B已发布n+1，A的n迟到返回
- **THEN** 角色侧条件写拒绝A，A不能覆盖B结果或释放B任务

#### Scenario: 旧租约失效但尚无新成功值
- **WHEN** A在发布前检查后发生租约接管，而B尚未成功发布
- **THEN** 协议允许A保存满足定位条件且高于已有版本的结果，B后续成功以更大版本替代
- **AND** 读者仍须校验当前scope，不能将旧scope结果视为当前有效值

#### Scenario: 角色写入结果未知
- **WHEN** 写入超时导致是否成功无法确定
- **THEN** 重读到本代次及scope后才确认；无法重读时保留任务等待恢复，不猜测成功或无条件覆盖

### Requirement: 版本基础破坏时保守处理

系统 MUST 在队列意外缺失而角色已有发布版本、或队列版本低于角色成功版本时告警，不在活动消费者存在时从零重建。维护恢复 MUST 停止所有旧消费者/未决请求，以角色版本为下限恢复任务，不单独回滚队列。

#### Scenario: 误删除任务后角色仍有心法
- **WHEN** 榜单再次登记该角色
- **THEN** 在线登记不得从零创建可运行任务；需维护恢复确认后延续版本

### Requirement: 基础判定与辅助查询分离

系统 MUST 复用现有indicator胜场最多及最近40条取10胜多数/平票最近出现的基础口径，不足10胜按原口径回退indicator。缓存scope MUST 与统计目标一致，但不得把配置赛季宣称为上游样本赛季证明。未经契约核实不得新增“缺赛季字段即拒绝全部回退”的过滤。明确不匹配的上游目标 MUST 拒绝。

#### Scenario: 近期胜场与indicator不同
- **WHEN** 最近40条中的10胜多数为冰心而indicator为云裳
- **THEN** 使用共享原判定选择冰心，规范ID与最终心法一致，不要求装备或队友

#### Scenario: indicator未声明赛季
- **WHEN** 不足十胜但本轮有效indicator可按既有契约判定，响应未声明赛季
- **THEN** 沿用原基础回退行为，scope记录请求目标，不伪造本赛季样本证据

### Requirement: 后台串行有界并复用异步HTTP

系统 MUST 在已核对的单消费者部署下运行本功能，与QQ连接无关，复用现有异步HTTP能力；每角色只查询必要indicator/history，无内部重试叠加，控制请求总预算、角色总预算、间隔和有上限退避。取消 MUST 不继续发下一请求。认证/429 MUST 冷却并告警，不引入全局control和双心跳承诺。

#### Scenario: 重复启动或QQ离线
- **WHEN** 同进程重复启动后台或QQ未登录
- **THEN** 同进程只存在一个消费循环，QQ离线仍能刷新

#### Scenario: 请求超时或认证失败
- **WHEN** 请求超过总预算或响应票据错误
- **THEN** 结束本轮并安排退避/冷却，保留成功结果；进程冷却不宣称跨重启全局保持

#### Scenario: 多实例部署
- **WHEN** 多个bot共享数据库
- **THEN** 首版部署仅允许一个实例启用本刷新；原子任务领取不能被宣称为全局请求限流或热备选主
