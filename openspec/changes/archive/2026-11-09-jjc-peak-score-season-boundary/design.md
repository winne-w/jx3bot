# 14 日最高分排名跨赛季修复方案

日期：2026-11-09，北京时间。方案已确认并实施，11:05:23 重启发布，16 份结果重建及公网验收通过。以下保留方案阶段证据与设计；最终结果见 acceptance.md。

## 结论与线上证据

14 日最高分统计直接使用 `[anchor_timestamp - 14天, anchor_timestamp]`，未与快照所属赛季取交集。新赛季低分与旧赛季高分同时参与每个角色的最高分聚合，旧分数因此主导榜单。已保存结果与 API 缺失结果时的即时聚合均受影响。

只读查询生产公开 API 得到：

| 快照锚点 | 返回路径 | 返回条数 | 最高分对局早于开赛的条数 |
|---|---|---:|---:|
| 2026-11-09 03:00:10，1794164410 | 已保存结果，status=done、version=1，未标记 fallback_aggregate | 1000 | 1000 |
| 2026-11-09 09:41:54，1794188514 | 即时聚合，fallback_aggregate=true | 1000 | 1000 |

03:00 快照窗口起点为 2026-10-26 03:00:10。两个榜单首位均为 3256 分，来源对局 270215546，发生于 2026-10-27 20:08:29。本赛季竞技场开放时间是 `config.CURRENT_SEASON_START=2026-11-05`，北京时间零点。这里的 1000/1000 描述返回榜单最高分来源，并不表示这些角色本赛季没有比赛。

`season-history` 查询显示当前“苍生铸世”赛季有 8 个排名快照。此数量是排查时点的读数，正式修复前必须重新枚举。

- https://qike.rickchen.cn/jx3bot/api/jjc/ranking-stats/peak-score?timestamp=1794164410&score_type=game&range=top_1000&include_match_summary=false
- https://qike.rickchen.cn/jx3bot/api/jjc/ranking-stats/peak-score?timestamp=1794188514&score_type=game&range=top_1000&include_match_summary=false

本次核对了本地源码与线上响应，未登录生产服务器比较文件，也未查询生产 Mongo 原始参与者。现有证据已能复现问题并支持修复方向；准确的重新排名、参与者缺口和受影响持久化文档数量需在实现后的 dry-run 中核定。

## 根因与影响路径

1. `src/services/jx3/jjc_peak_score_ranking.py::generate_for_anchor()`：直接用锚点减 14 天；`is_done()` 只按锚点、分数类型、版本读取完成状态，旧结果会一直跳过。
2. `src/storage/mongo_repos/jjc_match_participant_repo.py::aggregate_peak_scores()`：只按对局时间窗口筛选，没有接收赛季边界；随后先按分数排序、按角色取第一条，最终截取前 1000。
3. `src/api/routers/jjc_ranking_stats.py::get_jjc_peak_score_ranking()`：缓存不存在或加载超时时，另行构造未截断的 14 天窗口；即使定时任务修好，这条路径仍会重新生成错误结果。
4. 同文件的最高分详情使用 `_load_peak_score_doc()` 单独读缓存，没有与主列表共用即时聚合逻辑。修复必须使列表、分布和详情使用相同赛季范围与有效结果规则。
5. 两个 HTML 入口的最高分文案只描述回溯 14 天，尚未说明赛季截断。

11 月 5 日的近期对局、同步窗口与心法对阵赛季隔离，不会自动约束这条独立的最高分聚合链路。

## 业务口径

对于已知所属赛季及开赛时间的快照：

```text
window_end   = anchor_timestamp
window_start = max(anchor_timestamp - 14 * 86400, snapshot_season_start_time)
合法对局     = window_start <= match_time <= window_end
```

以 2026-11-09 03:00:10 为例，应只统计 2026-11-05 00:00:00 至 2026-11-09 03:00:10 的对局。赛季满 14 天后自然恢复完整滚动 14 天窗口。统计仍基于所有本地已同步 3v3 参与者，以角色 global_id 取最高分，再排序和截取排名范围；不要求角色仍在当前推栏榜中。

分数定义继续为游戏分 `total_score`，缺失时使用 `score`；推栏分使用 `mmr`。共用聚合路径的 `game` 与 `tuilan` 一起修复。所有参与场数、来源对局数、来源参与者数、心法分布和详情都使用筛选后的相同数据范围。

时间边界统一使用 UTC+8 解析。缺失或无效的 match_time 不参与。开赛零点保留，前一秒排除；锚点之后的数据排除。

## 推荐技术方案

### 统一赛季范围解析与读取

在最高分 service 中集中解析快照上下文、生成统计窗口、校验缓存和执行聚合。定时任务、列表及心法详情均调用该编排；路由仅校验请求、裁剪范围和封装响应。`singletons.py` 只装配当前赛季名称及开赛时间。

先读锚点对应排名摘要，确认 `current_season`，避免任意时间戳或旧赛季快照直接套用当前配置。本赛季摘要使用当前配置的开赛边界；新增结果持久化所属赛季和开赛时间，之后切季仍可按结果中保存的所属赛季上下文读取。

对旧赛季已有结果保留原历史口径，不用当前开赛时间将其截成空榜。旧赛季缺少结果且无法取得其真实开赛日期时，明确返回 not_found/历史口径不可用，不猜测边界、不回退到当前赛季或跨季的即时聚合。摘要不存在或与边界冲突时同样拒绝生成并记录原因。历史完整赛季配置表不在本次修复范围内。

### 聚合前过滤，完整重新排名

把截断后的 window_start 传入 `aggregate_peak_scores()`，在 Mongo pipeline 的首个 `$match` 应用；来源计数复用相同 query。先过滤、再取每个角色的最高分、再排序和 limit。

禁止仅过滤已存的 items：一个角色旧赛季 3200、本赛季 1800，正确结果应保留该角色的 1800；旧 items 已丢失这个候选，直接删除无法恢复。原先被旧高分挤出前 1000 的角色也需要从参与者中重新纳入。

本次以 `match_time` 作为赛季判断依据，不把 `season_id` 精确匹配设为新增硬前提。参与者 season_id 是依据写入时配置推导的投影标签，历史记录可能为空；强制要求会引入额外全量回填依赖。赛季隔离依然由实际发生时间和快照赛季边界严格保证。

先沿用现有时间/分数字段索引，对两种分数执行 explain 和耗时检查；仅在实测不达标时增加索引，不因本次边界收窄直接建设新索引。

### 缓存有效性与结果结构

保留现有 `anchor_timestamp + score_type + version` 唯一键及 version=1 的 API 兼容方式，为本次新结果增加：

| 字段 | 作用 |
|---|---|
| `aggregation_scope=season_bounded_v1` | 区分已按赛季截断的新结果与旧结果 |
| `season_id` | 对应快照的赛季名称 |
| `season_start_time` | 该赛季 UTC+8 开赛时间戳 |
| `window_start/window_end` | 实际参与计算的范围 |

这里使用额外 scope 标记，不需要修改所有调用方的 version 参数。读缓存与 `is_done()` 均检查 status、scope、所属赛季、开赛边界与期望窗口。当前赛季缺少这些标记的旧 done 结果必须失效；列表和详情均不得返回。`load_result()` 的 `$slice` projection 及状态查询 projection 必须同步包含校验字段。

已修正且持久化了所属赛季上下文的历史结果继续保留；旧赛季 legacy 结果只在其历史快照下展示，不用于本赛季结果兜底。

定时生成使用严格存储错误传播：写入失败不得报告 generated/done。重建有效结果时，先计算并验证候选，再单文档原子发布，避免先标记 processing 破坏可用结果。失败不覆盖已有的有效结果。旧的失效结果即使保留在库里也不能重新展示。

API 未命中统一用上述 service 和范围规则执行只读即时聚合，不借此写库；列表、分布及详情的范围裁剪和心法筛选均来自相同规则下的结果。当前赛季聚合失败应返回明确错误，不回退到旧跨季结果。

### 前端说明与缓存

同步修改 `public/jjc-ranking-stats.html` 与 `public/index.html`。文案说明“回溯前 14 天，最多至所选赛季开赛时间；不足 14 天按实际天数统计”，并展示后端实际窗口。旧赛季 legacy 数据继续使用原有历史口径说明，避免文案错误声称旧结果已经过修正。

页面缓存键增加最高分口径标识，发布时更新静态资源并刷新页面；分布、列表与展开详情都验证来自相同口径。榜单不足 1000 人时显示实际人数，不引入旧赛季补位。

## 线上存量修复与发布

1. 只读预检：按摘要的 current_season 和锚点时间枚举本赛季所有快照，检查摘要赛季与时间是否一致，核定已存 game/tuilan 结果与缺失项。排查时有 8 个锚点，即两类分数共 16 个候选组合；这不等于有 16 份已存错误文档。
2. 在现有 `_diagnostics` 交付方式下留存预检证据，生产侧备份候选结果文档和相关源码；不清理历史对局与参与者。
3. 增加定向重建工具，提供 dry-run/apply/verify 模式、显式赛季/锚点选择及强制重算选项。默认 dry-run，输出旧/新条数、旧赛季最高分来源数、成员变化、分数变化与窗口。不在方案阶段执行线上重建。
4. 先上线共享范围与缓存校验逻辑及两个前端入口，重启 bot 载入配置，确认旧进程退出；恢复期缓存缺失可按正确范围即时聚合。避免旧定时任务继续写入未截断结果。
5. 优先重建最新快照及用户查看的 03:00 结算快照，再分批重建本赛季剩余全部锚点的两类分数；不只处理每日 09:00 自动任务选取的最近两个。
6. 重建完成重新枚举一次，补齐修复期间新出现的锚点；核验所有新结果和 API 响应，再刷新前端进行展示验收。

拟新增工具尚未实现；正式执行命令在方案确认后的执行计划中给出，不能将本节参数描述当作现有可执行命令。

## 验证与验收标准

实现后应覆盖：

- 同一角色旧赛季 3200、本赛季 1800：结果为 1800；仅旧赛季有记录的角色消失；被旧分挤出排名的本赛季角色正确补入并连续编号。
- 开赛零点前一秒、零点本身、锚点本身、锚点之后一秒及缺失时间；新赛季不足 14 天和已超过 14 天两种窗口。
- 缓存命中、缺失、超时、旧 done 失效、有效 done 跳过、强制重建、写库失败及重复运行；失败不能假报成功或退回旧口径。
- game/tuilan、前 1000/200/100/50、分布/列表/心法详情的同口径；来源计数与参与场数同步过滤。
- 旧赛季快照仍可查看；历史边界未知不错误重算；再次切季后修正过的历史结果仍使用其持久化边界。
- 修改后的 pipeline 在隔离 Mongo 用真实聚合验证，并进行 explain 检查；不在生产库运行自动化测试。

复用 `tests/test_jjc_peak_score_ranking.py`、`tests/test_jjc_match_participant_repo.py`、`tests/test_jjc_ranking_stats_router.py`、`tests/test_jjc_ranking_stats_frontend.py`、`tests/test_jjc_data_center_navigation.py`，补充独立的定向重建测试；保持 Python 3.9 兼容。

线上验收要求：所有修正结果项都满足实际时间窗口，开赛前来源条数为 0；分布人数与展开详情一致；定时与即时结果在相同数据视图下相同；新生成锚点延续正确范围。最终条数可能少于 1000，不能预先承诺满榜。页面只代表本地已同步对局，无法通过本次修复补全尚未收录的比赛。

方案阶段只完成只读 API 复现与源码核对，尚未运行实现测试，也未核定正确榜单的实际分数与人数。

## 风险、回滚与文档联动

聚合与详情可能因同步增量在两次请求间变化，验收一致性需固定同一持久化结果或同一数据视图，不能把新增比赛引起的变化误判为口径不一致。重建按锚点顺序限并发，监测 Mongo CPU、扫描量与响应耗时。

发布异常时恢复备份源码和两个 HTML 入口并重启。新增字段为兼容字段，旧读取可忽略；已修正结果优先保留，除非确认数据写坏才按明确清单恢复受影响结果文档。回退到旧聚合逻辑会重新暴露问题，因此回滚恢复服务后仍须记录缺陷状态，不能视为验收通过。

实施时联动更新 `PROJECT_CONTEXT.md`、`docs/design-docs/database-design.md`、`docs/references/runbook.md`、README API 说明及 `openspec/specs/jjc-ranking/spec.md`，记录新范围、缓存有效性、重建与回滚路径。
