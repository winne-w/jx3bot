## Purpose

提供可按时间、双方任意心法组合和双方队伍平均游戏分区间查询的 JJC 3v3 对阵统计，并分页浏览唯一对局、下钻现有完整详情，以支持配置胜率与逐场奇穴研究。

## ADDED Requirements

### Requirement: 使用统一心法目录查询任意组合
系统 SHALL 提供服务端心法元数据，并允许配置 A 与配置 B 分别选择 0～3 个心法 ID；非空配置按无序多重集合的“包含”语义匹配到一支三人队伍。

#### Scenario: 页面加载心法目录
- **WHEN** 页面请求组合对阵元数据
- **THEN** 系统以统一响应结构返回按展示顺序排列的心法 ID、名称、类别、图标标识和展示序号，以及时间预设、分页大小、最大时间范围、分数范围、单边心法数和最大页码

#### Scenario: 单心法对阵单心法
- **WHEN** 用户查询配置 A 为奶秀、配置 B 为明教
- **THEN** 系统返回一边包含奶秀且另一边包含明教的对局，不限制其余四个心法

#### Scenario: 混合数量的组合对阵
- **WHEN** 用户查询配置 A 为策藏、配置 B 为气明歌
- **THEN** 系统匹配一边同时包含策藏且另一边同时包含气纯、明教、长歌的对局

#### Scenario: 队内选择顺序不影响结果
- **WHEN** 用户使用相同心法但改变同一配置内的选择顺序
- **THEN** 系统返回相同的唯一对局集合和统计值

#### Scenario: 重复心法按数量匹配
- **WHEN** 一个配置包含重复的同一心法 ID
- **THEN** 系统仅匹配对应队伍中该心法出现次数不少于查询次数的对局

#### Scenario: 单边配置为空
- **WHEN** 配置 A 或配置 B 为空而另一边非空
- **THEN** 系统将空配置解释为任意队伍，并统计非空配置对阵任意另一队的数据

#### Scenario: 双方配置为空
- **WHEN** 配置 A 与配置 B 都为空
- **THEN** 系统返回时间与分数条件内的全部可查询对局，但不建立配置胜负方向

#### Scenario: 查询历史有效心法 ID
- **WHEN** 请求包含不在当前页面目录中但格式合法的历史正整数心法 ID
- **THEN** 系统仍按该 ID 查询历史事实，不因目录未展示该 ID 而拒绝请求

#### Scenario: 非法配置参数
- **WHEN** 任一配置包含超过三个心法，或心法 ID 不是正整数
- **THEN** 系统返回统一错误响应且不执行统计查询

### Requirement: 按双方队伍平均游戏分筛选
系统 SHALL 为每名玩家优先使用 `total_score`、缺失时回退到 `score` 作为游戏分，并且仅在双方各三名玩家分数都完整、双方平均分都落入左闭右开区间时纳入胜率与分页结果。

#### Scenario: 双方平均分命中区间
- **WHEN** 两支队伍各自三人平均游戏分都满足 `score_min <= score_avg < score_max`
- **THEN** 系统将该对局纳入有效对局统计和分页结果

#### Scenario: 仅一方平均分命中区间
- **WHEN** 只有一支队伍的平均游戏分落入所选区间
- **THEN** 系统不将该对局纳入有效对局统计或分页结果

#### Scenario: 玩家游戏分缺失
- **WHEN** 匹配时间和配置条件的结构有效对局中至少一支队伍有玩家游戏分缺失
- **THEN** 系统不将该对局纳入胜率和分页结果，并将其计入缺失分数对局数

#### Scenario: 规范化玩家游戏分
- **WHEN** 玩家分数是整数、值为整数的有限浮点数、规范十进制整数文本或数值 0
- **THEN** 系统将其精确规范化为整数，保留 0，先尝试 `total_score` 再在其无有效值时回退到 `score`

#### Scenario: 玩家游戏分非法
- **WHEN** `total_score` 和 `score` 都是布尔值、负数、超过 1000000、非有限数、非整数数值、空文本或无法解析的文本
- **THEN** 系统将该玩家的游戏分视为缺失而不截断、取绝对值或使用 truthiness 推断

#### Scenario: 平均分精确边界
- **WHEN** 队伍平均游戏分恰好等于下限或上限
- **THEN** 系统包含等于下限的对局并排除等于上限的对局，且判断不受页面显示舍入影响

#### Scenario: 非法分数区间
- **WHEN** 分数边界不是整数、超出 `0..1000000`，或分数下限不小于分数上限
- **THEN** 系统返回统一错误响应且不执行统计查询

### Requirement: 使用明确的时间和分页请求合同
系统 SHALL 通过 `POST /api/jjc/matchups/search` 接受 Unix 秒时间范围、分数区间、双方心法 ID 数组和页码参数，并以项目统一响应结构返回结果。

#### Scenario: 使用快捷时间范围
- **WHEN** 用户选择最近 1、3、7 或 14 天
- **THEN** 页面以发起查询时刻为结束时间计算滚动 `N * 24` 小时时间窗，并向 API 提交绝对 Unix 秒

#### Scenario: 使用自定义日期范围
- **WHEN** 用户选择自定义开始和结束日期
- **THEN** 页面按 `Asia/Shanghai` 本地日界生成左闭右开的绝对 Unix 秒范围，并以结束日期次日 00:00 作为排他上界以包含用户选择的结束日期全天

#### Scenario: URL 恢复时间范围
- **WHEN** 页面执行查询或用户打开已分享的查询 URL
- **THEN** URL 保存并恢复绝对 `start_time` 和 `end_time`，同一 URL 重放相同时间窗口而不是重新计算“最近 N 天”

#### Scenario: 不使用缓存时间筛选
- **WHEN** 对局发生时间位于查询范围外但同步、缓存或投影时间位于范围内
- **THEN** 系统不纳入该对局

#### Scenario: 非法时间范围
- **WHEN** 时间字段不是正整数 Unix 秒、开始时间不早于结束时间，或范围超过 14 天
- **THEN** 系统返回统一错误响应且不执行统计查询

#### Scenario: 合法分页参数
- **WHEN** 请求省略页码参数或传入合法值
- **THEN** 系统默认 `page=1`、`page_size=20`，并只接受 `1 <= page <= 100000` 且 `page_size` 为 20、50 或 100

#### Scenario: 非法请求体
- **WHEN** 请求体不是 JSON 对象、字段类型错误或分页参数非法
- **THEN** 系统使用 `{"status_code": 非零值, "status_msg": "...", "data": {}}` 结构返回参数错误，而不是返回未包装的框架校验响应

#### Scenario: 损坏的 JSON 请求体
- **WHEN** 请求正文声明为 JSON 但存在语法错误
- **THEN** 路由捕获解析失败并返回相同的项目统一参数错误结构

### Requirement: 返回无结论的原始对阵统计
系统 SHALL 返回唯一有效对局数、方向样本数、双方胜场与百分比胜率、双向命中数和缺失分数对局数，但 MUST NOT 推断或返回优势方结论。

#### Scenario: 单方向命中
- **WHEN** 一场分数有效对局仅能将配置 A 匹配到一队并将配置 B 匹配到另一队
- **THEN** 系统为该场生成一个方向样本，并按实际胜方累计配置 A 或配置 B 的胜场

#### Scenario: 双方向命中
- **WHEN** 一场分数有效且处于所选区间的对局双方都同时满足配置 A 与配置 B
- **THEN** 系统将该场计为一个唯一对局、两个方向样本、配置 A 一胜一负、配置 B 一胜一负，并将双向命中数增加一

#### Scenario: 统计恒等式
- **WHEN** 至少一个配置非空且查询成功
- **THEN** `total = match_count`、`orientation_sample_count = match_count + bidirectional_match_count` 且 `team_a_wins + team_b_wins = orientation_sample_count`

#### Scenario: 胜率计算
- **WHEN** 方向样本数大于零
- **THEN** 双方胜率分别按 `wins / orientation_sample_count * 100` 计算并四舍五入到一位小数

#### Scenario: 有方向但零样本
- **WHEN** 至少一个配置非空但没有分数有效且处于区间内的对局
- **THEN** 系统返回双方胜场为 0、双方胜率为 null、方向样本数为 0、双向命中数为 0

#### Scenario: 单边配置为空的胜场含义
- **WHEN** 配置 A 非空而配置 B 为空
- **THEN** 配置 A 胜场表示包含 A 的队伍获胜次数，配置 B 胜场表示其任意对手队伍获胜次数；双方都包含 A 时该场按双向规则各贡献一胜一负

#### Scenario: 交换双方配置
- **WHEN** 用户交换配置 A 与配置 B 后以相同时间和分数条件重新查询
- **THEN** 唯一对局数保持不变，双方胜场和胜率互换

#### Scenario: 双方为空时浏览全部对局
- **WHEN** 配置 A 与配置 B 都为空
- **THEN** 系统返回唯一对局数、缺失分数对局数和分页数据，将方向样本数与双向命中数设为 0，并将双方胜场及胜率设为 null

#### Scenario: 返回客观数据
- **WHEN** 查询成功
- **THEN** 响应不包含优势、劣势、均势、置信区间或样本充分性结论

### Requirement: 分页浏览唯一对局并查看详情
系统 SHALL 按对局发生时间和整数对局 ID 倒序确定性分页返回唯一对局摘要，并允许用户通过现有对局详情能力查看六名玩家、装备和奇穴。

#### Scenario: 返回对局摘要
- **WHEN** 用户查询到有效对局
- **THEN** 每条摘要包含对局 ID、时间、地图、时长、源 `team1/team2` 顺序下双方三个玩家的心法和游戏分、双方平均分、胜负及 `matched_orientations`

#### Scenario: 表达匹配方向
- **WHEN** 对局仅正向、仅反向、双向或双方配置为空
- **THEN** `matched_orientations` 分别返回 `["forward"]`、`["reverse"]`、`["forward", "reverse"]` 或 `[]`，且系统不为展示重排源 `team1/team2`

#### Scenario: 双向命中详情去重
- **WHEN** 一场对局产生两个方向样本
- **THEN** 该对局在分页列表和分页总数中只出现一次

#### Scenario: 事实集合不变时稳定分页
- **WHEN** 查询条件与事实集合在两次分页请求之间保持不变
- **THEN** 系统以 `match_time DESC, match_id DESC` 返回确定、稳定且不重复的分页结果

#### Scenario: 分页期间事实变化
- **WHEN** 实时同步或历史回填在用户切换页码期间新增或更新命中事实
- **THEN** 后续页允许反映最新事实，用户刷新查询后以最新总数重新浏览

#### Scenario: 分页元数据
- **WHEN** 查询成功
- **THEN** 顶层 `total` 等于 `statistics.match_count`，且 `has_more` 等于 `page * page_size < total`

#### Scenario: 页码超出末页
- **WHEN** 页码合法但超出最后一页
- **THEN** 系统返回成功的空 `items`、不变的统计与总数以及 `has_more=false`

#### Scenario: 查看奇穴
- **WHEN** 用户点击分页列表中的一场对局
- **THEN** 页面使用该场 `match_id` 调用现有对局详情接口并展示包括奇穴在内的完整详情

#### Scenario: 空结果
- **WHEN** 时间、配置和分数条件内没有有效对局
- **THEN** 系统返回成功的空分页并同时展示缺失分数对局数，不进一步猜测候选是配置不匹配还是分数落在区间外

### Requirement: 提供独立的组合对阵统计页面
系统 SHALL 提供独立页面用于编辑组合查询条件、查看统计摘要和分页对局，并允许通过 URL 恢复和分享查询状态。

#### Scenario: 默认打开页面
- **WHEN** 用户首次打开页面且 URL 没有查询条件
- **THEN** 页面默认选择最近 7 天、空的双方配置和空的分数区间，并在用户填写合法分数区间前禁用查询

#### Scenario: 选择双方配置
- **WHEN** 用户为任一边添加或移除 0～3 个心法
- **THEN** 页面以标签展示选择结果并按所选多重集合提交心法 ID

#### Scenario: 交换双方
- **WHEN** 用户点击交换双方
- **THEN** 页面交换配置 A 与配置 B，并在重新查询后交换对应胜场和胜率展示而不改变源队伍展示顺序

#### Scenario: URL 恢复查询
- **WHEN** 用户刷新或打开包含合法查询参数的页面 URL
- **THEN** 页面恢复绝对时间、分数、双方配置、页码和每页数量并可重放相同输入

#### Scenario: 回显规范化筛选条件
- **WHEN** 查询成功
- **THEN** 响应回显绝对时间、分数和页码，并将每边心法 ID 升序排列且保留重复项

#### Scenario: 页面路径与 API 路径
- **WHEN** 页面在本地或生产映射下访问组合对阵能力
- **THEN** 本地页面使用 `/public/jjc-matchups.html`，生产页面使用 `/jx3/jjc-matchups.html`，API 使用部署配置的 `/jx3bot` 前缀访问仓库内 `/api/jjc/matchups/*` 路由

### Requirement: 仅从结构有效的 3v3 详情构建事实
系统 SHALL 仅为具有正整数对局 ID、正整数实际发生时间、两支各三名玩家队伍、六个正整数心法 ID 且双方胜负互斥的 3v3 详情保留统计事实；玩家分数缺失不使结构有效事实失效。

#### Scenario: 构建结构有效事实
- **WHEN** 详情具备合法 ID 和时间、两队各三人、六个合法心法 ID、显式类型为 3 或未提供类型、且恰有一队获胜
- **THEN** 系统创建或覆盖该对局事实，并根据分数完整性设置是否可进入分段统计

#### Scenario: 统一提取实际发生时间
- **WHEN** 外层保存 payload、详情和 `basic_info` 中存在一个或多个可解析时间字段
- **THEN** 系统依次使用外层 payload、详情、`basic_info` 的 `match_time/start_time` 兼容字段，记录冲突但不回退到缓存时间、投影时间或当前时间

#### Scenario: 分数缺失但结构有效
- **WHEN** 详情满足结构要求但一名或多名玩家游戏分缺失
- **THEN** 系统保留事实、标记分数不完整，并允许其进入缺失分数计数

#### Scenario: 显式类型冲突
- **WHEN** 详情显式声明非 3v3 类型，即使双方人数合计为六人
- **THEN** 系统不保留该对局统计事实

#### Scenario: 结构不完整或胜负非法
- **WHEN** 缺少实际发生时间、任一队不是三人、任一心法 ID 缺失或非法、双方都胜或双方都未胜
- **THEN** 系统不保留该对局统计事实，也不将其计入缺失分数数

#### Scenario: 详情变为不可用或非法
- **WHEN** 已有事实对应的主详情后来保存为 unavailable、非 3v3 或结构非法
- **THEN** 系统按源版本条件把同一对局更新为 inactive tombstone，保留版本水位并清除查询字段，使其不再被统计或分页查询

### Requirement: 对局级统计数据可重建且最终一致
系统 SHALL 以完整对局详情为主事实，在确认主事实保存成功后刷新轻量统计事实，并提供防旧写覆盖、安全、幂等的历史回填和核验能力。

#### Scenario: 主事实保存成功
- **WHEN** 一场详情已被 MongoDB 确认保存成功
- **THEN** 统一持久化编排分别尝试身份投影、玩家投影和对局事实投影，且所有详情保存入口最终遵循相同顺序

#### Scenario: 主事实保存失败
- **WHEN** MongoDB 未能保存对局详情
- **THEN** 系统记录主事实保存失败且不创建、覆盖或清理任何派生事实

#### Scenario: 派生投影失败
- **WHEN** 完整对局详情保存成功但身份、玩家或统计事实中的任一派生投影失败
- **THEN** 系统保留完整详情、继续尝试其他派生、记录可定位的投影失败，并允许后续回填修复

#### Scenario: 重复投影同一源版本
- **WHEN** 同一对局详情源版本被重复保存或重复回填
- **THEN** 系统只保留一条内容一致的最新事实

#### Scenario: 较旧来源晚到
- **WHEN** 历史回填尝试在较新实时投影之后写入同一对局的旧源版本
- **THEN** 系统拒绝旧写覆盖，并在核验统计中记录跳过数量

#### Scenario: 较旧有效来源晚于失效来源
- **WHEN** 较新 unavailable 或非法来源已写入 inactive tombstone，随后较旧有效回填尝试写入同一对局
- **THEN** 系统依据 tombstone 保留的源版本拒绝旧写，使已失效对局不会重新进入统计

#### Scenario: 相同源时间内容冲突
- **WHEN** 两次投影具有相同 `source_cached_at` 但规范源摘要不同
- **THEN** 系统记录冲突且不以不确定顺序覆盖；只有时间与摘要都相同且 schema 更高时才重建派生字段

#### Scenario: 默认运行历史回填
- **WHEN** 运维人员未显式指定写入确认参数而运行历史回填
- **THEN** 工具只读取和输出可写入、缺分、结构跳过、待失效、旧版本跳过与异常数量，不修改数据库

#### Scenario: 显式执行历史回填
- **WHEN** 运维人员在核对 dry-run 后显式确认写入
- **THEN** 工具按稳定整数对局 ID 水位分批写入 active 事实或 inactive tombstone，重复运行结果一致且不会用旧源覆盖新事实

#### Scenario: 核验事实一致性
- **WHEN** 运维人员运行只读核验
- **THEN** 工具报告缺失事实、孤儿事实、应失效事实、源摘要不一致、schema 版本错误和构建失败数量
